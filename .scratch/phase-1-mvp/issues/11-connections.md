# 11 — Связи: список, происхождение, «смотрели»

**What to build:** Страница связей хозяйки: взаимно / слежу / смотрели, у
каждой связи — строка происхождения («подарила колье — оно в зале славы»,
«скинулись вместе», «заходил дважды»). Связи не добавляются вручную — только
из подарка (тикет 10) или визита зарегистрированного гостя по открытой ссылке.

**Blocked by:** 10.

**Status:** done

- [x] Страница связей (турн 21): фильтры Все/Взаимно/Слежу/Смотрели, строка происхождения из Connection.origin+history
- [x] Визит зарегистрированного гостя в чужую комнату создаёт/обновляет Connection kind=VIEWED (дедуп по паре, счётчик визитов в history)
- [x] Подарок из receiveGift создаёт связь и «зовёт» гостя (если у брони есть guestUserId/email — предложение «остаться на связи» на экране гостя) — см. Comments: связь создаётся сразу и без подтверждения, отдельного экрана согласия в Phase 1 нет
- [x] В API нет и не будет поиска людей/импорта контактов (негативный тест: таких роутов нет)
- [x] Односторонняя подписка — легитимное состояние; взаимность выводится, не запрашивается

## Comments

- **Решение по контракту 10-го (из двух предложенных вариантов): вынос, а не
  пост-обработка.** Inline-создание Connection в транзакции `receiveGift`
  заменено вызовом `upsertGiftConnection(tx, …)` из нового сервиса связей —
  внутри ТОЙ ЖЕ транзакции (атомарность «Дошло» не тронута, все 19 тестов
  10-го зелёные, включая тест отката по FK). Почему так, а не пост-обработка
  history после транзакции: (а) связь и её history пишутся атомарно с
  переходом — не бывает связи без счётчика и счётчика без связи; (б) дедуп
  зеркальной пары и апгрейд VIEWED всё равно требовали заменить inline-блок,
  пост-обработка оставила бы два места правды. Критерий выполнен: строка
  происхождения на странице связей получает данные при каждом «Дошло».
- **Модель: ОДНА строка Connection на пару людей, в любой ориентации.**
  Перед созданием ищутся обе ориентации (a,b) и (b,a) — зеркальный дубль не
  рождается (контракт Comments 10-го). Счётчики history направленные, поэтому
  одна строка честно читается с двух сторон:
  `{giftsToA, giftsToB, lastGiftAt, lastGiftItemId, lastGiftTitle,
  visitsByB/lastVisitByBAt (гость b смотрел комнату a),
  visitsByA/lastVisitByAAt (зеркальный случай)}`.
- `src/server/services/connections.ts` (новый), поверхность — ровно четыре
  функции (allowlist под негативным тестом):
  - `recordVisit(viewerUserId, roomOwnerId)` — VIEWED у хозяйки
    (a=хозяйка, b=гость, origin `visit`), дедуп пары и зеркала; инкремент
    визитов не чаще 1/час на направление (спам-заслон: F5 — не «N визитов»);
    существующий kind НЕ трогается вообще (визит не понижает FOLLOW/MUTUAL);
    origin существующей строки не переписывается (происхождение = рождение
    связи); своя комната — no-op; гонка первых визитов гасится P2002 → no-op.
  - `recordVisitBySlug(viewerUserId, slug)` — резолв ника И короткого кода
    (порядок как в guest-room), false → 404 роутом.
  - `upsertGiftConnection(tx, {receiverUserId, giverUserId, itemId, itemTitle})`
    — из транзакции receiveGift. Пары нет → создать (a=получатель,
    b=даритель, kind MUTUAL при комнате дарителя, иначе FOLLOW — правило
    10-го, origin `gift:{itemId}`, history {giftsToA:1, lastGift*}). Пара
    есть → kind/origin не перезаписываются (тест 10-го), ЕДИНСТВЕННЫЙ
    апгрейд: VIEWED → FOLLOW/MUTUAL (подарок сильнее «смотрели», понижения
    не существует); history обновляется всегда (направленный счётчик
    получателя +1, lastGift*).
  - `listConnections(userId, {kind?})` — строки обеих ориентаций, DTO-allowlist
    собеседника: displayName ?? name, avatarUrl — и НИЧЕГО больше (ни email,
    ни даже userId собеседника — под тестом ключей и regex'ом). Происхождение
    отдаётся СТРУКТУРОЙ `origin: {type:"gift", received, given, lastTitle,
    lastInHall} | {type:"visit", visits} | {type:"link"}` — строки собирает UI
    через next-intl (CLAUDE.md: все строки через messages), «она в зале славы»
    проверяется по живой вещи (state/inHall/hiddenFromHall). Legacy-строки
    10-го без history читаются из origin `gift:{itemId}` (название вещи
    подтягивается батчем). Сортировка — по последнему событию.
- `bookItem` (services/bookings): второй ОПЦИОНАЛЬНЫЙ параметр
  `{sessionUserId?}` — все 60+ существующих вызовов не тронуты. Пишет
  `booking.guestUserId`, когда гость залогинен; своя вещь → отказ
  **OWN_ITEM** (403 в роуте): подарок себе не бывает, бронь без дарителя
  врала бы счётчику. Роут book берёт sessionUserId ТОЛЬКО из сессии (телу
  не доверяется), auth — ленивый import под try/catch: вне runtime Next
  (vitest) гость честно аноним, суточные тесты 08-го зелёные без правок.
- Пинг визита: `POST /api/v1/rooms/{slug}/visit` (новый роут) — без сессии
  204 no-op, с сессией recordVisitBySlug, неизвестный слаг 404, всегда
  no-store. Клиент: fire-and-forget fetch в `booking-context.tsx` (один
  useEffect после первого рендера). HTML комнаты по-прежнему одинаков для
  всех — инвариант кэшируемости 07-го жив, «смотрели» ездит отдельным
  некэшируемым запросом (как «занято»).
- UI `/connections` (page.tsx + connections-list.tsx, турн 21): «Связи · N»,
  подстрока «X взаимно · Y слежу · Z смотрели», чипы Все N/Взаимно/Я слежу/
  Смотрели (клиентский фильтр, активный залит акцентом комнаты), строки:
  аватар (или силуэт), имя, бейдж kind, строка происхождения, relativeTime
  «N дней назад»; VIEWED приглушены (как в макете). Пустое состояние тихим
  тоном: «Связи появляются из подарков и открытых ссылок — добавлять руками
  нечего». НИ одной формы, ни route.ts/actions.ts в каталоге (под негативным
  тестом). Ссылки: /room — «Связи» в шапке рядом с «Зал славы»; /room/occasion
  — тихая «Связь появилась — посмотреть →» под списком, появляется когда есть
  отмеченные «Дошло» (после клика router.refresh() приносит её сам).
