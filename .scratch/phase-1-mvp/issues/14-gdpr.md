# 14 — GDPR: экспорт и полное удаление аккаунта

**What to build:** В настройках: «скачать мои данные» (один JSON-файл: профиль,
комната, вещи, брони моей комнаты без имён гостей до раскрытия, связи) и
«удалить аккаунт» с подтверждением — полный каскад в БД + чистка файлов в S3.

**Blocked by:** 13.

**Status:** done

- [x] POST /me/export → JSON-файл со всеми данными пользователя; имена гостей в активных (нераскрытых) бронях НЕ входят в экспорт хозяйки (инвариант тихой брони распространяется на экспорт — тест)
- [x] DELETE /me: подтверждение фразой, каскад Prisma, удаление S3-ключей (аватар, фото вещей), выход из сессии
- [x] Гостевые брони удалённой комнаты исчезают; «мои брони» гостя показывают «комната удалена»
- [x] Тест: после удаления в БД нет ни одной строки пользователя

## Comments

- **Сервис** — `src/server/services/account.ts` (новый):
  - `buildExport(userId)` → JSON-объект: user (email/displayName/locale/
    avatarKey/createdAt), room (preset/zoneSet/zonesOff/shareSlug/nick/
    occasionDate/demoGhostsOff — набор по заметке тикета 13), items (ВСЕ,
    включая hidden, allowlist всех полей; price строкой), `bookings:
    {takenCount}` — счётчик берётся у `ownerTakenCount` (инвариантный канал
    тикета 09), connections обеих сторон (ТОЛЬКО kind/origin/createdAt — без
    чужих email). Сериализация только allowlist — ключей guestName/guestEmail/
    cancelToken в форме экспорта НЕ СУЩЕСТВУЕТ (под тест-регексом).
    giverName РАСКРЫТЫХ вещей входит естественно — это поле самой вещи.
    Комнаты нет (до онбординга) → room:null, экспорт всё равно отдаётся.
  - `deleteAccount(userId, storage?)`: (1) ДО удаления собираются roomId и
    известные ключи (photoKey вещей, avatarKey; фильтр «только наши»
    items/ | avatars/ — заслон в глубину); (2) ОДНА транзакция:
    `user.delete` (каскад: Account, Session, Room→Item→Booking→
    PoolContribution + PriceSnapshot, Connection обеих сторон — удаление
    юзера рвёт и чужие связи С ним, так и задумано) **плюс явные deleteMany
    по моделям БЕЗ FK на User**: OccasionSummary (по roomId), ParseJob и
    RecognitionJob (по userId), VerificationToken (по identifier=email) —
    схема их каскадом не заденет, а GDPR требует; (3) ПОСЛЕ коммита — S3:
    СПИСОК известных ключей ∪ листинг префиксов `items/{roomId}/` и
    `avatars/{userId}/` (сироты от прежних смен — заметка 13) одним
    deleteObjects. Ошибка S3 операцию НЕ валит: console.error + возврат
    `{s3Cleaned:false}` (аккаунт уже удалён — это главное обещание).
    `storage` — инъектируемый шов (как putObject в image-ingest).
  - `DELETE_ACCOUNT_PHRASE = "удалить комнату"` — канон фразы один на все
    локали; страница передаёт его в клиент пропом (клиент НЕ импортирует
    серверный модуль).
- **S3** — `src/server/s3.ts` (дополнение, существующее не тронуто):
  `listKeysByPrefix(prefix)` — ListObjectsV2 с пагинацией по

  вычистим ВЕСЬ бакет); `deleteObjects(keys)` — DeleteObjects батчами по
  1000 (лимит API), Quiet-режим, частичный отказ → исключение (решает
  вызывающий; GDPR-чистка логирует и не валит).
- **Экспорт-роут** — `GET /api/v1/me/export` (auth; в тикете писалось POST,
  сделан GET — скачивание файла ссылкой без JS, семантика чтения):

- **Тикету 16 (чистка/сироты)**:
  1) deleteItem/смена аватара/замена фото ПО-ПРЕЖНЕМУ не чистят старые
     S3-объекты при ЖИВОМ аккаунте — копятся сироты; теперь есть готовые
     кирпичи `listKeysByPrefix`/`deleteObjects` (s3.ts) — джоба-сборщик
     пишется поверх них тривиально;
  2) `{s3Cleaned:false}` после deleteAccount сейчас только логируется —
     некому повторить чистку (кандидат: BullMQ-джоба s3.cleanup с ретраями,
     ключи/префиксы в payload);
  3) RecognitionJob.imageKey живёт в ПРИВАТНОМ бакете (S3_PRIVATE_BUCKET) —
     наши listKeysByPrefix/deleteObjects работают только с основным;
     когда распознавание оживёт (Phase 2), чистку приватного бакета
     добавить отдельно (строки в БД уже удаляются);
  4) экспорт отдаёт photoKey/avatarKey ключами, не файлами — «архив с
     фотографиями» (zip) сознательно за рамками MVP, кандидат при первом
     же запросе пользователей.
