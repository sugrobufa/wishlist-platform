# 19 — Вход по ссылке: не сгорает заранее, вошедшего не спрашивают снова
(приёмка п.8 и п.9)

**What to build:** Ссылка из письма доводит человека до комнаты с первого
раза, даже если браузер или почтовый сканер «потрогали» её раньше; уже
вошедший не видит форму входа.

**Blocked by:** None. **Чинить до выхода на реальную почту (VPS).**

**Status:** done

## Что происходит сейчас

1. Токен одноразовый и тратится первым же GET. Chrome при вводе URL в адресную
   строку делает предзагрузку → токен сгорает до того, как человек нажал Enter
   → «Verification error». То же сделают корпоративные антивирусы/сканеры
   почты, которые открывают ссылки за пользователя. Воспроизведено на приёмке
   дважды подряд.
2. `/signin` не проверяет сессию: после успешного входа страница снова
   показывает «Ссылка отправлена» — человек думает, что вход не сработал.

## Критерии

- [x] Ссылка из письма ведёт не на прямой callback, а на промежуточную
      страницу подтверждения («Вход в комнату» + одна кнопка): токен
      расходуется только по действию человека (POST), предзагрузка и сканеры
      его не тратят. Страница не должна требовать JS для отправки формы
- [x] Токен по-прежнему одноразовый и с прежним сроком жизни; переход по
      странице подтверждения без токена/с протухшим — человеческое сообщение
      и кнопка «прислать новую ссылку» (не сырой `error=Verification`)
- [x] `/signin` (и страница подтверждения) редиректят уже вошедшего в `/room`
- [x] Письмо и dev-консоль печатают новую ссылку; **формат консольной рамки
      `✉  [magic link]` сохранить байт-в-байт** — на неё завязан перехват в
      e2e (`E2E_MAIL_FILE`, тикет 15)
- [x] Тексты через next-intl (ru + en), тон продукта
- [x] e2e full-cycle обновить под новый шаг подтверждения — он должен
      остаться зелёным; плюс unit на «вошедшего редиректит»

## Comments

### Каким путём завершается верификация и почему он безопасен

Выбран вариант (а) тикета: форма страницы подтверждения делает обычный
`POST` в **настоящий callback провайдера** —
`/api/auth/callback/nodemailer?token=…&email=…&callbackUrl=/room`.

Проверил по исходникам пакета, что путь законный, а не «случайно работает»:

- `@auth/core/lib/index.js` — в POST-ветке `case "callback"` CSRF-проверка
  (`validateCSRF`) вызывается **только** для провайдера `credentials`;
  email-провайдер её не требует;
- `@auth/core/lib/actions/callback/index.js` — ветка `provider.type === "email"`
  читает `query?.token` и `query?.email`, метод запроса ей безразличен.
  Поэтому token/email лежат в query формы, а не в скрытых полях.

Значит, вся проверка осталась внутри Auth.js: тот же
`adapter.useVerificationToken` (строка удаляется в момент использования), та
же сверка `expires`, тот же `maxAge` 24 ч, та же выдача сессии и cookie.
Своей валидации токена и своей работы с сессиями в коде **нет** — вариант (б)
(ручной разбор `VerificationToken` + создание сессии через адаптер) означал бы
повторение внутренностей пакета: хеш `sha256(token+secret)`, имена cookie,
`useSecureCookies`, срок сессии. Это ломается на первом же обновлении
next-auth и легко разъезжается с настоящим флоу.

Почему это безопасно:

- **Одноразовость и срок жизни не тронуты** — их по-прежнему обеспечивает сам
  Auth.js; изменился только момент вызова: не GET из письма, а POST по кнопке.
- **GET страницы не обращается ни к токену, ни к адаптеру.** Предзагрузка
  адресной строки Chrome, почтовый антивирус и корпоративный сканер видят
  статичный экран. Проверено вживую: два GET подряд — токен в БД жив, сессия
  не выдана; вход после них работает.
- **CSRF тут нечего защищать**: без самого токена подделать POST нельзя, а
  токен есть только у владельца почты. Действие формы — вход, оно и так
  рассчитано на один клик человека.
- **Токен не расползается**: страница `noindex`, Referer с токеном уходит
  только на наш же origin (как и раньше у прямой callback-ссылки).

### Решения по мелочам

- `callbackUrl` формы — `/room`: он сам уводит в `/onboarding`, если комнаты
  ещё нет (`src/app/room/page.tsx`), поэтому отдельной развилки не появилось.
- `pages.error` Auth.js направлен на ту же страницу подтверждения: любой отказ
  входа (`Verification` и прочие) приходит на наш тихий экран с кнопкой
  «Прислать новую ссылку» — сырого экрана Auth.js человек больше не видит.
- Рамка `✉  [magic link]` не изменилась ни на байт: в `src/server/mailer.ts`
  правок нет вообще, новый адрес собирает вызывающий
  (`src/server/auth-links.ts` → `magicLinkUrl`).
- `vitest.config.ts`: добавлен `server.deps.inline: ["next-auth"]` — иначе
  юниты не могут позвать настоящий обработчик Auth.js (next-auth импортирует
  `"next/server"` без расширения, а у пакета `next` нет поля `exports`, и
  нативный ESM-загрузчик Node такой путь не находит).
