# Как выложить комнату в интернет

Инструкция для владельца. Всё, что нужно сделать руками, — здесь, по шагам.
Команды можно копировать целиком. Ничего в коде править не придётся.

---

## Что вообще происходит

Ваш сервер — обычный компьютер, который всегда включён и виден из интернета.
Мы поставим на него **Docker**: это как коробки, в каждой живёт своя часть
сервиса и не мешает соседям. Коробок шесть:

| Коробка      | Что делает                                                       |
| ------------ | ---------------------------------------------------------------- |
| **caddy**    | принимает посетителей, сам выпускает и продлевает сертификат HTTPS |
| **app**      | само приложение — комнаты, вещи, брони                            |
| **worker**   | фоновые дела: письма, скачивание фото, закрытие праздника         |
| **postgres** | база данных                                                       |
| **redis**    | очередь фоновых дел                                               |
| **minio**    | хранилище картинок                                                |

Сборка приложения происходит **не на сервере**, а на бесплатных машинах
GitHub: сервер маленький, а сборка тяжёлая. Готовая «коробка» кладётся в
хранилище образов GitHub, сервер её просто скачивает. Поэтому выпуск новой
версии занимает секунды и почти не нагружает сервер.

**Один выпуск = одна кнопка.** После первой настройки каждое изменение в
коде уезжает на сервер само: прошли проверки — приложение обновилось.

## Что понадобится

- Адрес сервера: **155.212.143.124**

- Доступ в панель Beget и в настройки репозитория на GitHub.

## Шаг 1. Положить публичный ключ на сервер

Это делаете вы, в панели Beget.

1. Откройте файл `~/.ssh/wishlist_deploy.pub` (именно **.pub**) и скопируйте
   его содержимое целиком — одна длинная строка, начинается с `ssh-ed25519`
   или `ssh-rsa`.

   На Windows в PowerShell:

   ```powershell
   Get-Content $HOME\.ssh\wishlist_deploy.pub
   ```

2. В панели Beget: раздел **VPS → ваш сервер → SSH-ключи** (или «Доступ»).
   Добавьте новый ключ, вставьте скопированную строку, сохраните.
   Если панель предложит применить ключ к серверу — согласитесь.

3. Проверьте, что вход работает. В PowerShell:

   ```powershell
   ssh -i $HOME\.ssh\wishlist_deploy root@155.212.143.124 "echo вход работает"
   ```

   Должно напечатать `вход работает`. Если спрашивает пароль — ключ не
   применился, вернитесь к пункту 2. **Дальше не идите, пока не заработает.**

## Шаг 2. Настроить сервер (один раз)

Подключитесь к серверу:

```powershell
ssh -i $HOME\.ssh\wishlist_deploy root@155.212.143.124
```

Дальше команды выполняются **на сервере** (приглашение сменится на
`root@...:~#`). Скачайте и запустите скрипт первичной настройки:

```bash
curl -fsSL https://raw.githubusercontent.com/ВЛАДЕЛЕЦ/wishlist-platform/main/deploy/bootstrap.sh -o bootstrap.sh
sudo bash bootstrap.sh
```

> Если репозиторий закрытый и ссылка не открывается — просто скопируйте
> содержимое файла `deploy/bootstrap.sh` из репозитория, создайте на сервере
> `nano bootstrap.sh`, вставьте, сохраните (Ctrl+O, Enter, Ctrl+X) и
> запустите `sudo bash bootstrap.sh`.

Скрипт идёт минут пять и сам делает всё: ставит Docker, заводит пользователя
`deploy`, закрывает лишние двери (снаружи остаются открытыми только 22, 80 и
443), включает защиту от подбора паролей, добавляет подкачку памяти и
автообновления безопасности.

**Важно.** В конце он отключает вход по паролю — остаётся только вход по
ключу. Он сделает это, только если найдёт ваш ключ на сервере (шаг 1). Пока
скрипт работает, **не закрывайте это окно**. Когда допишет — откройте
**второе** окно и проверьте вход заново:

```powershell
ssh -i $HOME\.ssh\wishlist_deploy deploy@155.212.143.124 "docker --version"
```

Должна напечататься версия Docker. Теперь первое окно можно закрывать.

## Шаг 3. Создать файл настроек на сервере

В файле `.env` лежат пароли от базы и хранилища. Он живёт **только на
сервере** — ни в интернете, ни в репозитории его нет.

На сервере (под пользователем `deploy`):

```bash
ssh -i ~/.ssh/wishlist_deploy deploy@155.212.143.124
cd /opt/wishlist
```

Сначала сгенерируйте три случайных пароля и **сохраните их у себя** (в
менеджере паролей). Команда напечатает три строки:

```bash
echo "AUTH_SECRET      = $(openssl rand -base64 32)"
echo "POSTGRES_PASSWORD= $(openssl rand -hex 24)"
echo "S3_SECRET_KEY    = $(openssl rand -hex 24)"
```

Теперь создайте файл:

```bash
nano /opt/wishlist/.env
```

Вставьте это и подставьте свои значения вместо `…`:

```ini
APP_IMAGE=ghcr.io/ВЛАДЕЛЕЦ/wishlist-platform
APP_TAG=latest

APP_DOMAIN=155-212-143-124.sslip.io
APP_BASE_URL=https://155-212-143-124.sslip.io
ACME_EMAIL=ваша-почта@example.com

AUTH_SECRET=…
AUTH_TRUST_HOST=true

POSTGRES_USER=wishlist
POSTGRES_PASSWORD=…
POSTGRES_DB=wishlist
DATABASE_URL=postgresql://wishlist:ТОТ_ЖЕ_ПАРОЛЬ@postgres:5432/wishlist

REDIS_URL=redis://redis:6379

S3_ACCESS_KEY=wishlistminio
S3_SECRET_KEY=…
S3_ENDPOINT=https://155-212-143-124.sslip.io
S3_BUCKET=wishlist
S3_PRIVATE_BUCKET=wishlist-private
CDN_BASE_URL=

EMAIL_SERVER=
EMAIL_FROM=room@localhost

PARSER_UA="WishlistBot/1.0"
CATALOG_ENABLED=false
RECOGNIZE_ENABLED=false
```

Сохраните: **Ctrl+O**, Enter, **Ctrl+X**. И закройте файл от посторонних:

```bash
chmod 600 /opt/wishlist/.env
```

> `ВЛАДЕЛЕЦ` в первой строке — ваш логин на GitHub, маленькими буквами.
> `ТОТ_ЖЕ_ПАРОЛЬ` — ровно то же значение, что в `POSTGRES_PASSWORD`.
> Полный список переменных с пояснениями — в `.env.prod.example`.

### Почему адрес такой странный

Домена пока нет, а HTTPS нужен уже сейчас. `155-212-143-124.sslip.io` — это
бесплатная служба, которая превращает IP-адрес в имя. Имя настоящее, значит
на него выдаётся **настоящий сертификат**: в браузере будет замок, без
предупреждений. Когда купите домен — поменяете три строки (см. ниже).

## Шаг 4. Три секрета в GitHub

Откройте репозиторий на GitHub → **Settings** → **Secrets and variables** →
**Actions** → кнопка **New repository secret**. Добавьте три штуки:

| Имя (Name)       | Значение (Secret)                                             |
| ---------------- | ------------------------------------------------------------- |
| `DEPLOY_HOST`    | `155.212.143.124`                                             |
| `DEPLOY_USER`    | `deploy`                                                      |
| `DEPLOY_SSH_KEY` | всё содержимое файла `~/.ssh/wishlist_deploy` (без `.pub`!)   |

Для третьего — скопируйте файл целиком, **вместе со строками**
`-----BEGIN OPENSSH PRIVATE KEY-----` и `-----END OPENSSH PRIVATE KEY-----`:

```powershell
Get-Content $HOME\.ssh\wishlist_deploy | Set-Clipboard
```

GitHub спрячет это значение навсегда: посмотреть его потом нельзя, только
заменить. Так и должно быть.

---

## Шаг 5. Первый выпуск

GitHub → вкладка **Actions** → слева **Deploy** → справа кнопка
**Run workflow** → зелёная **Run workflow**.

Первый раз идёт минут 8–12 (собирается образ). Дальше — 2–3 минуты.

Когда всё позеленеет, откройте в браузере:

**https://155-212-143-124.sslip.io**

Должна открыться заглавная страница с замком в адресной строке.

> Если браузер ругается на сертификат — подождите минуту и обновите:
> Caddy получает сертификат в первые секунды после старта.

Дальше выпускать ничего вручную не надо: любое изменение в `main` проходит
проверки и уезжает на сервер само.

## Вход, пока нет почты

### Быстрый способ: одна закладка

Если в `/opt/wishlist/.env` стоит `QUICK_LOGIN_ENABLED=true` и заполнен
`QUICK_LOGIN_EMAIL` (см. `.env.prod.example`), достаточно открыть:

```
https://155-212-143-124.sslip.io/dev-login
```

и вы внутри — без ключа, без формы, без вопросов. Этот адрес и есть закладка.

**Онбординг заново.** Экран первого запуска показывается один раз в жизни
аккаунта — ровно пока у вас нет комнаты. Чтобы пройти его снова:

```
https://155-212-143-124.sslip.io/dev-login?fresh=1
```

Этот адрес пускает внутрь и **стирает вашу комнату целиком**: вещи, брони,
вклады в складчину, сводки праздников, связи и фото вещей в хранилище. Сам
аккаунт, имя и вход остаются — по дороге вас не разлогинит. Операция
необратима и отмены не имеет. Трогает она только вашу комнату — ту, что на
`QUICK_LOGIN_EMAIL`; параметры в адресе на это не влияют, «чужую» стереть
этим маршрутом нельзя.

**Посмотреть пустую комнату, ничего не стирая** (тикет 190):

```
https://155-212-143-124.sslip.io/dev-login?empty=1
```

Это вход **вторым пользователем стенда** — тем, у кого комната заведомо пустая
(её заводит `npx prisma db seed`, почта в `QUICK_LOGIN_EMPTY_EMAIL`). Он ничего
не сеет и ничего не стирает: ваша комната остаётся как была, а первый экран
новичка можно смотреть сколько угодно. Обратно — обычный `/dev-login`.

**Ключ теперь необязателен.** `QUICK_LOGIN_SECRET` можно оставить пустым —
так и задумано. Если он всё-таки заполнен (24+ символа), старая ссылка
`?key=…` продолжает работать, а ссылка с *неверным* ключом отвечает 404 —
в этом случае просто откройте `/dev-login` без ключа. Ключ лежит в `.env` на
сервере:

```bash
ssh -i ~/.ssh/wishlist_deploy deploy@155.212.143.124 "grep QUICK_LOGIN_SECRET /opt/wishlist/.env"
```

Это **временный обход**, пока нет почты, и он открыт: кто знает адрес — тот
войдёт в комнату владельца. Пока адрес стенда знаете только вы, это
осознанный размен ради приёмки. Когда почта заработает — поставьте
`QUICK_LOGIN_ENABLED=false` и перезапустите приложение
(`docker compose -f docker-compose.prod.yml up -d`): маршрута снова не
существует, на любой адрес `/dev-login` сервер отвечает 404.

### Способ без ключа: ссылка из журнала

Почта не подключена, поэтому ссылка для входа **не отправляется, а
печатается в журнал приложения**. Это нормально и достаточно, чтобы
пользоваться сайтом самому.

1. На сайте нажмите «Войти», введите свою почту, отправьте.
2. На сервере посмотрите журнал:

   ```bash
   ssh -i ~/.ssh/wishlist_deploy deploy@155.212.143.124
   cd /opt/wishlist
   docker compose -f docker-compose.prod.yml logs --tail=50 app | grep -A1 "magic link"
   ```

3. Увидите такое:

   ```
   ✉  [magic link] you@example.com
      https://155-212-143-124.sslip.io/signin/confirm?...
   ```

   Скопируйте ссылку целиком и откройте в браузере. Вы внутри.

Письма гостям (напоминания, «что подарили») до подключения почты тоже
никуда не уходят — они печатаются в журнал **worker**:

```bash
docker compose -f docker-compose.prod.yml logs --tail=100 worker
```

## Когда появится домен

Три строки в `/opt/wishlist/.env` и одна команда.

1. У регистратора (или в панели Beget, если домен там) сделайте
   **A-запись**: `example.ru` → `155.212.143.124`. Подождите, пока
   заработает — обычно от минут до пары часов.

2. На сервере:

   ```bash
   ssh -i ~/.ssh/wishlist_deploy deploy@155.212.143.124
   nano /opt/wishlist/.env
   ```

   Поменяйте три строки (остальное не трогайте):

   ```ini
   APP_DOMAIN=example.ru
   APP_BASE_URL=https://example.ru
   S3_ENDPOINT=https://example.ru
   ```

3. Примените:

   ```bash
   cd /opt/wishlist
   docker compose -f docker-compose.prod.yml up -d
   ```

Сертификат на новый домен Caddy получит сам, за несколько секунд. Старый
адрес `…sslip.io` продолжит работать — он никуда не делся.

> Уже загруженные фотографии останутся доступны: приложение раздаёт их
> своим адресом `/media/…`, а не прямой ссылкой на хранилище.

## Когда появится почта Beget

1. В панели Beget заведите ящик, например `room@example.ru`, и задайте ему
   пароль.
2. На сервере откройте `/opt/wishlist/.env` и заполните две строки:

   ```ini
   EMAIL_SERVER=smtps://room%40example.ru:ПАРОЛЬ@smtp.beget.com:465
   EMAIL_FROM=room@example.ru
   ```

   Собака в логине пишется как `%40` — это не опечатка. Если в пароле есть
   `@`, `:`, `/` или `#`, их тоже надо заменить (`%40`, `%3A`, `%2F`, `%23`)
   — или просто задать в панели пароль из букв и цифр.

3. Примените:

   ```bash
   cd /opt/wishlist && docker compose -f docker-compose.prod.yml up -d
   ```

Проверка: запросите ссылку для входа на сайте — письмо должно прийти на
почту, а в журнале приложения его больше не будет.

## Как откатиться, если новая версия сломала сайт

**Обычно откатываться не нужно** — автоматика делает это сама. После
каждого выпуска она проверяет, отвечает ли приложение; если нет — сразу
возвращает предыдущую версию и помечает выпуск красным.

Если всё же надо вернуться руками:

```bash
ssh -i ~/.ssh/wishlist_deploy deploy@155.212.143.124
cd /opt/wishlist
cat .last-good-tag          # последняя версия, которая точно работала
./deploy/release.sh sha-XXXXXXX
```

Или из GitHub: **Actions → Deploy → Run workflow**, в поле «Тег образа»
вписать нужный (`sha-1a2b3c4`) и запустить.

> Откатывается приложение, но **не база**. Если новая версия успела изменить
> структуру базы, чистый откат может не помочь — тогда восстанавливают из
> бэкапа (ниже). Поэтому база меняется осторожно и обратно совместимо.

## Бэкапы

Копия базы — один сжатый файл в `/opt/wishlist/backups/`.

**Снять прямо сейчас:**

```bash
cd /opt/wishlist && ./deploy/backup.sh
```

**Делать каждую ночь автоматически** (один раз настроить). На сервере:

```bash
crontab -e
```

Откроется редактор; добавьте в конец одну строку и сохраните:

```
30 3 * * * cd /opt/wishlist && ./deploy/backup.sh >> /opt/wishlist/backups/backup.log 2>&1
```

Это «каждый день в 3:30 ночи». Копии старше 7 дней удаляются сами.

**Посмотреть, что есть:**

```bash
ls -lh /opt/wishlist/backups/
```

**Скачать копию к себе** (раз в месяц — хорошая привычка: копия на том же
сервере не спасёт, если пропадёт сам сервер):

```powershell
scp -i $HOME\.ssh\wishlist_deploy deploy@155.212.143.124:/opt/wishlist/backups/wishlist-*.sql.gz .
```

**Восстановить из копии** (сотрёт текущие данные — только осознанно):

```bash
cd /opt/wishlist
gunzip -c backups/wishlist-20260805-0330.sql.gz | \
  docker compose -f docker-compose.prod.yml exec -T postgres psql -U wishlist -d wishlist
docker compose -f docker-compose.prod.yml restart app worker
```

## Шпаргалка команд

Все выполняются на сервере из `/opt/wishlist`. Чтобы не писать длинное
`-f docker-compose.prod.yml` каждый раз, можно один раз выполнить:

```bash
echo 'export COMPOSE_FILE=/opt/wishlist/docker-compose.prod.yml' >> ~/.bashrc && source ~/.bashrc
```

Тогда работает просто `docker compose …`:

| Что нужно                | Команда                                    |
| ------------------------ | ------------------------------------------ |
| Всё ли живо              | `docker compose ps`                        |
| Журнал приложения        | `docker compose logs -f --tail=100 app`    |
| Журнал фоновых дел       | `docker compose logs -f --tail=100 worker` |
| Перезапустить приложение | `docker compose restart app worker`        |
| Поднять всё после ребута | `docker compose up -d`                     |
| Сколько занято памяти    | `docker stats --no-stream`                 |
| Сколько занято диска     | `df -h /` и `docker system df`             |
| Проверить здоровье       | `curl -s "https://$(sed -n 's/^APP_DOMAIN=//p' .env \| tr -d '\r')/api/health"` |

Ответ здоровья выглядит так:

```json
{ "data": { "status": "ok", "db": "up", "redis": "up", "version": "sha-1a2b3c4" } }
```

`status: ok` — всё хорошо. `degraded` — приложение работает, но очередь
недоступна (письма подождут). `down` — недоступна база, сайт не работает.

## Если что-то пошло не так

**Сайт не открывается совсем.**
Проверьте, что коробки подняты: `docker compose ps` — у всех должно быть
`running`, у `app` ещё и `healthy`. Если какая-то `restarting` — смотрите
её журнал: `docker compose logs --tail=100 ИМЯ`.

**Браузер ругается на сертификат.**
Подождите 1–2 минуты после первого старта. Если не прошло — журнал Caddy:
`docker compose logs --tail=50 caddy`. Частые причины:

- домен ещё не указывает на этот сервер (для настоящего домена) или закрыт
  порт 80 — проверка Let's Encrypt ходит именно в него;
- в журнале написано про **rate limit**. Такое возможно с временным адресом
  `…sslip.io`: этим именем пользуются многие, и лимит выдачи на сутки
  бывает исчерпан. Лечится двумя способами — подождать несколько часов
  или взять адрес-близнец у соседней службы: поменять в `.env` три строки
  на `155-212-143-124.nip.io` (и `https://155-212-143-124.nip.io`) и
  выполнить `docker compose -f docker-compose.prod.yml up -d`. Работает
  ровно так же. С настоящим доменом этой проблемы нет вообще.

**Выпуск покраснел в GitHub.**
Откройте Actions → упавший запуск → шаг, где красный крестик. Если это шаг
«Release», автоматика уже вернула предыдущую версию — сайт работает,
чинить можно спокойно.

**Кончилось место.**
`docker system df` покажет, что занимает. Обычно это старые образы приложения:
каждый выпуск весит около 1.6 ГБ, а диска 14 ГБ.

Уборка «старше недели» (`prune --filter "until=168h"`) здесь **не работает** —
выпуски идут по нескольку в день, и все образы моложе. Убирать надо адресно,
оставляя нынешний тег и предыдущий (на него откатывается `release.sh`):

```bash
docker images --format '{{.Repository}}:{{.Tag}}' | grep wishlist-platform
docker rmi ghcr.io/<владелец>/wishlist-platform:sha-<старый>
```

Если диск занят на 100%, `docker rmi` ответит `gc failed`: сборщику мусора
тоже нужно немного места. Снимите теги всё равно — место освободится, когда
сборщик доработает; проверяйте `df -h /`, а не сообщение об ошибке.

С 06.08.2026 `deploy/release.sh` убирает старые образы сам после каждого
принятого выпуска, так что руками это должно понадобиться только при разборе
старой поломки.

**Приложение отвечает, но медленно.**
`docker stats --no-stream`: если `postgres` уперся в лимит памяти — стоит
взять тариф побольше. Лимиты заданы в `docker-compose.prod.yml`, менять их
осмысленно только вместе с объёмом памяти сервера.

## Где что лежит

| Файл                          | Что это                                        |
| ----------------------------- | ---------------------------------------------- |
| `/opt/wishlist/.env`          | пароли и настройки (только на сервере)         |
| `/opt/wishlist/docker-compose.prod.yml` | описание всех шести коробок          |
| `/opt/wishlist/deploy/Caddyfile` | настройки HTTPS и заголовков                |
| `/opt/wishlist/deploy/release.sh` | выпуск версии с откатом                    |
| `/opt/wishlist/deploy/backup.sh` | бэкап базы                                  |
| `/opt/wishlist/backups/`      | сами бэкапы                                    |
| `/opt/wishlist/.last-good-tag` | последняя версия, прошедшая проверку          |

Данные (база, файлы, сертификаты) лежат в томах Docker и переживают любой
перезапуск и обновление. Удалять их может только команда с `-v` — её без
крайней нужды не пишите.
